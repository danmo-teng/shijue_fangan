# 人参与决策的上下位机协作流程

更新：2026-11-08。本文件只维护协作原则；具体任务和实施范围见当前STATUS/TODO。

## 强约束：不让旧上下文污染当前任务

旧聊天、压缩摘要、补丁、历史交接及另一端AI的要求，不自动成为本次任务、限制或授权。
只依据本次目标、当前适用范围和核对过的代码/证据推进；旧资料按需取证，不整包加载或转发。
阶段方向可调整，不因“以前确认过”固定架构；新证据改变重要取舍时向人说明，无新依据不反复询问。
这一原则不撤销当前明确有效的用户要求，也不要求把所有历史事项重新审批。

## 四步协作

1. **短提案。** 讲清实际问题、已证/未知部分、最小改法、代价和两端影响。细节只附相关项，不为小修复要求全套合同和验证。
2. **双方审查，人决定重要取舍。** 接收方看自己的代码，允许接受、缩小、替代或拒绝。已确认范围内直接推进，超范围先说明。
3. **最小实现及必要验证。** 检查调用链与资源影响，复用现有入口；编译、直接相关少量检查、已授权短实测。不重复堆测试或新系统。
4. **短回执。** 给实现与实际结果、未完成项、commit/push及必要的接口变化。固件另说明构建/实际身份/烧录状态，不以expected代替actual。

## 避免再次扩张要求

- 除明确保留的合爪检查，不擅自增加数据新鲜度、反复握手、资格确认或阻断运行的等待。
  对实际小功率器件的风险不能凭猜测扩张成保护/停机逻辑；有具体证据先解释，由用户决定。
  跨端任务单双向适用：发出建议不能夹带，收到对方新增限制必须先问用户是否执行，不能当自动授权。
  合爪业务检查不成为其他阶段新增限制的理由；下位机交接不附加未经用户要求的测试代码/测试程序任务。
- 附加时间检查当前默认不做（测试和比赛），包括仅诊断的高频计时/健康巡检。必要例外先解释证据、替代、成本和触发行为并取得用户同意。
- 不把普通异常默认升级为全车停机。丢样本、清VALID/ready、停注入、拒发和结束动作都要说明实际影响；人工STOP保持有效。
- 提案说明新增ISR/临界区/串口工作；优先复用已有机制，不默认扩遥测、诊断或错误处理框架。
- 交付对照批准范围核对实际diff和两端影响，不能以“仅诊断”夹带新门控，也不能把规则落地写成代码/实车已通过。
- 持久化只更新当前摘要与相关条目，清除过期状态。下位机规则是否落地，以其实际路径/提交回传为准。

>
> 规则和代码改动都提交推送GitHub，回传路径/SHA、检查结果与未完成项；有接口变化才附对应合同/示例。固件实际身份、expected、构建和烧录状态分开。核对实际diff没有夹带未讨论的要求，不能声称未回传的另一端规则已同步。

## 固定的双向请求入口

双方仓库统一使用docs/CROSS_REPO_REQUESTS.md，放最新相关请求及审核/实现回执。
本轮涉及跨端接口或用户通知对端更新时，由AI读取对端GitHub固定入口并更新本端相关内容，
不再让用户常规手动复制；镜像标明来源提交及请求ID，不把旧版覆盖为新要求，不整包导入历史。
请求至少区分：用户批准的目标/范围、接收方方案审核、具体实现、实际部署和未完成项。
文档发布和读取不等于审核通过或实施授权；重要取舍仍须讲给人，由人选择、调整或拒绝。
已经批准的具体范围可以继续小步实施，不能借新流程增加一轮无意义批准。

默认不写对端固件或烧录。文档写入也受实际权限限制；不足时一次性建立固定入口，
之后读取对端源文件、同步本端要求和回执。不能声称没有完成的同步、审核或烧录已完成。
具体入口与启用状态见CROSS_REPO_REQUESTS和PROJECT_STATUS；不是后台自动执行服务。
用户说transfer时仍按AGENTS中的文件交换约定处理，但它不再是常规请求的唯一送达方式。
