# 相机故障恢复提速与节点时刻记录

用户本轮明确批准：缩短故障后的缺节点等待，并记录节点恢复等时刻。该许可仅用于本次故障恢复，不扩展成健康运行巡检、数据年龄门控或新的动作握手。横移速度需求独立交下位，未混入相机代码。

## 实现范围

- 相机已关闭、正在恢复时，约每200ms检查已选稳定by-id路径及其目标节点是否存在；没有节点就不创建相机/解码器/管线。原目录未解析成功时，按同节奏复用原解析器，不任挑多个相机。
- 节点出现后尝试打开。节点存在但实际打开失败时，保留原首次约1秒、后续约2秒的低频重试；期间仍按200ms观察节点变化。重试间隔是恢复调度，不用于拒绝真实视觉/定位反馈。
- 健康图像流没有新增节点检查或阶段计时。故障期间不逐次写缺节点记录：仅状态变化、实际打开尝试及首帧/结果里程碑写日志；相同节点解析错误不刷屏。
- 保留原相机机械/管线准备、JPU失败切软件解码、比赛暂停/恢复、热模型及本局进度。换节点后保持全局vision_sequence递增，不重发CONFIG，不重启比赛。
- 未更改模型、阈值、ROI、帧率、抓取或分离流程；没有实际启动相机或底盘验证。

## competition_events.jsonl中的记录

每轮恢复用recovery_id关联，时间均用上位单调纳秒，可与原业务/UART日志对齐；不要依赖可能未校时的目录日期。

| 事件 | 记录的含义 |
| --- | --- |
| camera_recovery_started | 上位发现故障的时刻、设备路径、错误；运行中还记录当时上位状态及下位报告的模式/相机角/任务动作编号，并标明上下文是否有效 |
| camera_node_missing | 本轮首次发现节点不存在，或从存在变为不存在；持续缺失不重复写盘 |
| camera_node_present | 首次观察到节点存在/重新出现；附最后一次缺节点检查时刻及两次检查之间实际相隔多久 |
| camera_open_attempt | 真正开始创建/打开相机，不将轻量缺节点检查算作打开尝试 |
| camera_open_finished | 打开结束、成功/错误及耗时；首次启动失败若发生在诊断启动前，耗时记null，不补造0 |
| camera_first_frame_observed | 主循环首次看见恢复相机的解码帧：帧编号、该帧原有published_ns和主循环观察时刻、属于哪次打开 |
| camera_recovery_restored | 已获得识别结果并交给规划的时刻，以及本轮总耗时、节点/首帧/打开次数汇总；沿原恢复条件执行，不因只发现节点就发车 |

**节点存在不是相机已经出图。** 节点真实重新出现发生在最后一次“未见节点”与首次“看见节点”之间；轮询不能给出电气连接恢复的精确瞬间。正常轮询区间约200ms，线程调度或同步打开阻塞可能更长，日志写实际observation_gap_ms，不把200ms当保证值。如果从未观察到缺失，则下界为null，只能说观察到节点存在。

latest-frame相机会丢弃中间帧，主循环首次看见的帧不保证是相机第1帧；因此明确记录first_frame_id，复用该帧解码发布时刻，不冒充曝光/USB重新连接时刻。同一故障尚未恢复又失败时保留原recovery_id和开始时刻，防止总耗时被重新清零。

## 必要验证及仍待验证

7项离线检查通过，含原正式runner的运行中读取失败、JPU故障回退、实际临时目录中的节点移除/稳定链接改指新节点、全局帧号/CONFIG不重发；验证200ms检查、缺节点不构造相机、不刷缺失日志、打开失败低频重试与节点变化并存、三类恢复时刻分开、权限错误不伪造节点消失。未运行真实设备，不能宣称原约4.2秒已经降到某个数值。

下一次原故障发生后，依据节点观察区间、open_duration_ms和result_ready_monotonic_ns分清：节点迟迟不回来、管线打开慢，还是出图到识别结果慢。物理断流原因（线缆/供电/USB或驱动）仍未唯一确认。
