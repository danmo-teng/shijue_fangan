# 动态定位接入正式比赛：当前差距与最短路径

2026-11-04，RDK审查基线a35c02c；下位机GitHub main再次确认11eeacf。本次只审查/准备，没有启动比赛或修改运行配置。

结论：现有几何、官方轮速SDK输入和动态围栏处理可以复用；当前桌面程序不能直接替换正式比赛定位。
可马上准备适配，今天能否进入高速实车调试取决于下位机修复/任务模式反馈和最小场地验证，不承诺当天全流程通过。

## 代码里的实际差距

| 项目 | 已有代码 | 接入时必须处理的事 |
|---|---|---|
| 安装外参 | 正式`localization.example.conf`仍为forward=+x、up=-y、偏置(-0.020,-0.070)m；测试是新30°候选 | 正式新后端明确采用已确认候选，保持比例1.000，不把测试地图起点移植进去 |
| UART所有权 | 正式`rescue_map/map_app.py:682`启动C++定位器负责串口/命令转发；测试由F405 Python客户端负责 | 选择一个所有者；不能同时启动两个入口，也不能只将JSON路径指向测试输出 |
| 官方SDK输入 | `localization/src/main.cpp:334`明确要求debug轮速入口使用外部UART且TX关闭 | 当前正式启动参数与此入口不兼容，不能只加一个开关；SDK仍只开一个进程 |
| 任务传输 | 正式C++支持0x15/0x17/0x1E接收、0x16位姿和0x18＋0x1D转发；没有07/08混合解析 | 保留已有task/action配对、复位及命令转发语义，补实际测量通路，不用调试0x19控制替换比赛任务 |
| 定位发布 | 动态入口只写dynamic_status/轨迹日志，metadata明确control_pose_published=false | 将校正后车中心位姿发布给比赛JSON和0x16，避免planner和下位机分别使用两套位姿 |
| 时间采用 | `run_competition_rescue.py:182`与`state_machine.py:1056`仍有250ms位姿门；StmSnapshot.fresh及地图读取也有年龄逻辑 | 按用户政策处理现有年龄拒绝，未知时间如实保留；真实帧身份/任务配对与“年龄”分开，不顺手改审核业务 |
| 坐标 | 动态测试取四个90°对称解中初始车头最接近+X；正式有红蓝、1～4起点及安全区方向 | 正式使用已有场地定义选择对应坐标分支；不能把+X调试分支当红蓝绝对场地姿态 |
| 越障 | 现有动态页仅人工暂停/恢复墙修正 | 正式开局减速带需与已知越障阶段配合，缺墙时继续既有SDK/主yaw传播，不能把障碍表面当围栏；尚无自动遮挡验收 |
| 下位机构建 | F405是NormalDebugTask；NormalRun仍是F407；07/08当前仅运动调试构建启用 | 接收方确认精简遥测在任务模式的最小复用、波特率和构建；详见本轮修复交接 |

正式任务0x18并没有“把测试速度滑块设大”的语义。下位机当前导航/返中配置800mm/s、开局前进800mm/s，
测试入口最高命令700mm/s；这些都是设定值，不是已测实际速度。高速调参主要需要下位机配合，不能只改地图按钮。

## 证据够到哪一步

- 静止桌面213249会话：雷达10.08Hz、处理P95约49.5ms，Pose199.65Hz，实际SDK轮速API577次true，队列/日志丢弃0。
  证明通路和该负载下吞吐；没有证明围栏精度或和正式YOLO26同跑时的性能。
- 现场224334会话有真实动作和FAULT；没有独立ground_truth，不构成高速定位精度通过。
- 自由初始化已做离线几何/扫描检查，真实场地的新启动分支与越障行为还要确认。

## 推荐安排

1. 先完成F405-FAULT-01第一项，审查实际提交/烧录身份，复用现有地图做一段短直行、一次转动及STOP。
   时间质量未知不拦测试；观察动作是否被误停、轮速API计数是否持续增长、位置方向是否合理。桌面能回答的先做。
2. 同时准备正式接入文件与接口，复用YOLO26和原比赛状态机，采用可切换定位后端，保留旧入口可回退。
   不等待所有历史定位实验重跑；但不能把未接通的接口当完成。
3. 场地一次有目的短验证：已有实测标线的一段平移/一次转动、一次雷达暂停/恢复，检查方向、中心偏移和实际误差。
   随后在原比赛流程逐段提高到既定高速，检验真实导航/返中/越障，不一上来改变全部速度和算法参数。

不新增轮式位置加权、旧EKF跳变拒绝、永久停车判断或时间质量认证。安装候选、比例、pose jumping保持。
日志保留原始Pose、中心Pose、雷达校正结果、真实SDK调用、任务身份及人工实测；继续保护问题会话。

## 实现结构需要决定的取舍（本轮只给建议）

| 方案 | 收益 | 代价 |
|---|---|---|
| 推荐：保留正式C++ UART/任务转发所有者，给定位数据通路增加07/08和动态修正适配 | 保留已跑过的比赛命令/状态配对，不将比赛控制迁到调试客户端 | 需给现有接收器补混合协议/测量出口，并让唯一SDK接收轮速、统一发布校正位姿 |
| 复用测试Python UART所有者，迁入正式命令转发/状态配对 | 直接复用07/08和wheel bridge处理 | 需移植并核对正式转发、复位、0x17/0x1E配对、0x16发布，业务接口改动更广 |

两种都保留单一UART/SDK所有者；不能通过同时运行正式和测试程序省掉适配。
推荐先选第一种以减少比赛控制改动；具体实施前由用户决定，不在准备阶段偷偷改架构。
