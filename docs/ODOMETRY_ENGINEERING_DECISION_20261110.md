# 高频里程计、同步与降级方案定案

2026-11-10，审查代码基线2046c01。用户本轮优先处理TODO 3/4，并明确委托根据证据直接选择工程方案。本文件是选定的实施方案，**不是代码已接入或实车验证通过的回执**。本轮没有打开设备、发运动命令或清理日志；比赛业务修复、性能迁移和其他历史任务不自动恢复。

## 选定的主线

保留一个C++权威运动里程计：**正常使用连续T265锚点＋实测轮速未覆盖尾段；轮式有平移反证时采用T265连续增量；T265实际退化时采用轮速＋主yaw；雷达在扫描时刻校正可观测位置，再带到当前时刻。**

这不是把两套位置按权重相加，也不是无条件信任某个传感器。正常链本来就不是纯轮式：motion_source_native.cpp在每个成对Pose更新T265锚点，然后只用轮速补尾段。沿用这一已存在的结构，重点完善选源、连续性和时间关系，避免为换“高频基准”重写全部定位。

输出由真实轮/Pose事件驱动，目标维持至少100Hz可用更新，不靠重复旧样本凑数。T265选中时不必为了轮式100Hz再等待轮反馈；实际控制交付频率和延迟仍需原入口验证，不能由线程频率推定。

## 为什么这样选

本机T265有低延迟、约200Hz的实际输出，不能再把它当作响应很慢的备用传感器。但响应快与运动估计正确是两件事。已有同输入结果如下，单位mm，都是相对已接受墙位移的RMS，**墙面受原去畸变/先验影响，不是独立真值**：

| 数据分组 | 窗口数 | 轮式 | SDK位置 | SDK速度积分 |
| --- | ---: | ---: | ---: | ---: |
| 动态会话，窗口末处正常T265锚点＋轮尾段 | 8 | 18.25 | 15.03 | 18.84 |
| 正式第一场全部空间窗口 | 29 | 39.78 | 77.06 | 80.49 |
| 正式第二场全部空间窗口 | 52 | 36.89 | 353.14 | 179.04 |
| 正式第二场，不含已统计的>50mm SDK位置跳步 | 42 | 38.49 | 157.15 | 174.66 |

正常动态窗口没有支持“必须换掉T265”的证据；正式异常数据又明确不支持“低延迟所以全场信T265”。无>50mm跳步也不等于视觉跟踪正常，不能只修跳点就宣布慢漂移已解决。第一行按窗口末来源分组，并不证明整个窗口没有切源。数据来自现有priority_todo_20261110各组wall_windows.csv和motion_source_review.json，未重新拟合参数。

纯轮式在抵墙空转、单轮腾空和横移打滑时也会错，不能作为永远可信的唯一基础。因此采用当前分工结构，异常时明确换增量来源，而不是全场切SDK速度积分或只靠轮式硬撑。

## 三份历史及一次场地修正

1. 原始轮历史持续保存真实计数、测量区间、体速和来源身份，即使暂停采用也不修改/清零。
2. 原始SDK历史保存原始定位中心、车中心、姿态、速度、confidence及帧号；pose jumping继续开启。不能在原始日志里抹掉跳变。
3. 唯一选中里程计维护导航实际采用的连续增量及来源。切源在共同时间点重锚；排除期间的空转轮段以后也不能补回。导航和雷达去畸变使用同一条选中历史，不另养一套不同来源的轨迹。

场地坐标保持正式起点参考。雷达修正在扫描reference_ns计算：当前场地位置＝扫描时刻墙解＋该时刻之后选中运动的增量。motion_runtime.cpp现有apply_wall已具备这一关系，应保留；改源时先重建同一参考时刻的选中轨迹，再计算墙偏置，避免重复补偿或把计算完成时刻当采样时刻。单墙只修法向，沿墙方向仍由运动先验承担；两面不平行墙才提供完整XY。保持原围栏重获和场地对称分支。

## 选源和双异常

| 情况 | 选定行为 |
| --- | --- |
| 两路运动相容、没有反证 | 保留正常T265锚点＋真实轮尾段，不增加等待 |
| 墙位移支持T265、轮式XY有反证 | 用T265连续增量＋主yaw，排除轮式尾段并暂停SDK新轮速输入 |
| T265跟踪整体退化、轮式没有被证伪 | 用原轮式＋主yaw传播，雷达修正可观轴，保留异常原因 |
| 已排除轮式，而SDK只有平移坐标跳变 | 重建SDK连续里程计基准；只对跨跳的一个采样间隔使用同样本SDK车中心速度过桥，随后继续正常位置增量，不因这一下跳变恢复坏轮式 |
| SDK位置与速度均失真，轮式也有反证 | 显式记录双方可疑，依据最近同区间墙证据选择较有支持的运动；看不到墙且无法判明时，非业务排轮阶段沿用实际轮反馈作不确定退路，保留轮式可疑和SDK暂停状态，不冒称恢复 |
| 安全区业务明确排除轮式 | 保持不注入、不用空转尾段；SDK也进入连续性处理，不能绕过跳变分支。两路均无可信运动且墙也不可观时，保留最后可支持估计及未知分量，不能把位置保持解释成真实静止 |

最后一类属于既有业务排轮场景下缺少可用XY观测的边界：无可支持新运动时仍是既有的最后估计保持，不新增一条自动冻结位置的策略，也不把保持解释成真实静止。不以此新增全车STOP/FAULT、清VALID、握手或年龄拒绝。无墙＋轮滑＋视觉整体失效时，硬件没有足够独立信息，任何软件方案都不能保证完整XY准确。不能伪造另一条“必然正确”的速度，或把未知当作传感器已恢复。

### 区分位置重定位跳变与整体退化

官方v2.50.0说明pose jumping只改变平移位置，不改变旋转/速度/加速度。这给“仅跨跳一个采样间隔过桥”提供依据；并不保证SDK速度在视觉退化或坏轮影响下正确。

选中里程计的重基准关系是：`bias_new = selected_prev + delta_physical_bridge - raw_position_now`。后续选中位置为`raw_position + bias_new`，不用长期速度积分。桥接速度必须从SDK完整三维姿态/角速度做一次车中心杆臂修正，再投影到与位置相同的固定平面；不能用车体系速度直接加在地图XY，也不能重复补内部IMU偏移。

使用实际相邻帧区间、位置与速度的一致性及已存在的跳变证据，不能把真实长间隔运动全部当跳点。帧断裂、姿态/速度也异常的片段不能冒充纯平移重定位。本策略是维护导航连续参考，不删除SDK原始跳变、不开旧EKF位置拒绝门，也不关闭pose jumping；真实场地修正仍由墙几何承担。没有围栏时，单靠它不能校正长期漂移。

本轮原始日志复核：正式第二场frame43267在5.011ms内车中心跳212.65mm，同间隔速度积分约1.24mm，速度前后只差0.0088m/s、姿态转动约0.579°、confidence均3；frame43331再跳197.01mm，速度桥约0.396mm。业务排轮阶段也有9个50～89mm单帧跳步，而各自速度桥仅约0.2～0.8mm。现代码该阶段直接publish_vio，确实绕过跳变处理。部分其他跳步同时伴随约0.7m/s速度突变，不能一概按纯位置跳处理。

同一次双异常，固定前后墙端点的100.25ms/500ms窗口中，原SDK位置残差172.95/63.94mm、仅单帧过桥后43.25/55.12mm、原轮式14.39/36.84mm。过桥去掉了大跳，但并未解决剩余运动误差，仍不能称这段应当无条件采用SDK。这里为可行性把所统计的全部>50mm步长都过桥，**不等于在线已能可靠分类每个纯重定位跳变**。详见[派生复核](reports/t265_odom_decision_20261110.json)，原始数据未写入。

## 判滑证据及恢复

采用已有07三轮计数复算角增量，与有效主gyro按同一运动区间比较；先修相位关系。主gyro不是第二套编码器角速度。L=0.130m为当前模型，0.115m只是离线有效候选，不借判滑重新标定轮臂或速度比例。

角差只提供一个旋转约束：三轮滑移和为零时，前/左虚假速度仍可很大；反过来，三轮相同误差可能主要影响轮式角量而不改变XY。SDK输入没有编码器角速度形参，杆臂项使用主gyro，因此**不能仅因角差异常就判整组注入线速度错误**。角差用于提示、辅助归因；停送/选源由平移证据及既有业务排轮决定。

恢复依据必须针对先前出错的分量、来自冲突之后的实际运动；静止零角差不证明轮式XY已恢复。优先复用已有墙/运动一致性恢复条件，不增加固定等待或新握手。单墙不能确认另一个方向恢复，SDK也不能单独证明曾经注入它的轮速已正确。证据不足不新增暂停；已确认轮式错误又缺恢复证据时可以继续T265定位，不将暂停升级为永久故障停车。

原始T265 IMU残差可补充角差与瞬态速度变化，但不能发现全部匀速平移滑移。本轮不把采原始IMU、重力/偏置估计、双积分或整套Ground-Fusion当必需前置，不扩张高频回调负担。只有既有信号的盲区仍影响具体结果时，再按同一SDK所有者做必要小范围取证；不引入第二个SDK进程。

## 时间关系与官方注入

- 历史雷达/角残差查询使用约28ms的主gyro相位对齐工程初值，原始时戳和未知质量不改。该值来自多动作重复相位，尚不能分解模块滤波和时钟误差，也不是永久硬件标定。
- 当前航向采用已有数据验证的因果估计作为首个实现：主gyro场地角＋已收到角速度推进到当前已有运动端点。新值标为估计，不伪造新gyro帧；预测只随新的真实gyro源事件更新，同一旧源不因GUI/轮回调重复而继续积分，断流仍遵循既有支持末端保持。这是估计更新规则，不按年龄拒收反馈。SDK增量＋主rate补尾段留作之后有明确收益需求时的小步替代，不让SDK失效连带失去主yaw参考。
- 不把gyro时戳全局倒移后要求实时注入多等28ms；不为检测窗口先攒100ms再发旧轮速。SDK实际发送继续沿现有事件驱动路径，判据使用已到的过去区间。
- `v_C^C=R_CB*(v_B^B+omega_B^B×r_BC^B)`保持，实测体速与主gyro各自一次转换，SDK源T/W=0、噪声不调小；输入不能换成目标速度或T265速度。
- SDK v2.50.0实际发送的两个时间字段由固件接收时填入，frame_num不携带采样时间；API返回true没有融合权重/设备逐样本采用回执。不能把延迟样本批量补发，再称SDK已按历史回填。
- 单一motion_runtime/native决定导航来源及新轮速停/续，SDK所有者只执行。暂停不是发零速度，也不清除SDK此前轮速影响；恢复只从新的实际测量继续。暂停期间尚待gyro配齐的旧07也需消费/划清边界，不能在恢复后重放。

本轮额外复核两场正式的6833/9941个活动轮端点，严格仅取当时callback和processing都已完成的SDK样本。SDK通常仍缺最新8.28/8.82ms（中位）、12.10/14.14ms（P95）尾段；只有0.29%/0.49%端点被已处理SDK历史完整覆盖。相对后续对齐gyro代理的角差P95：主rate因果预测0.270/0.274°，SDK增量到最新可用帧后保持0.984/1.189°，SDK增量＋主rate尾段0.130/0.132°。最后者有潜力，但增加SDK依赖与时钟/切源关系；首步选更简单、对SDK故障独立可用的主rate方案。原生socket实际到达未单独记录，SDK支撑已是乐观可用界；代理不是场地角真值。完整方法与统计见[因果旋转桥复核](reports/t265_heading_bridge_20261110.json)，不把源相位接近当每个当前端点已被覆盖。

## 实施边界与交付顺序

1. 先在已有离线入口复核纯跳变过桥、正常/退化分组及双异常反例；原始日志只读。跳点桥接消除大跳不等于整段定位更准，必须留出墙端点和原轮式对照。
2. 在NativeMotionSource和Python回退同步落实连续基准、双方可疑语义及业务排轮分支；同一输入核对，SDK单所有者、原任务协议/正式起点保持。不能只改显示轨迹而控制仍取另一条位置。
3. 接入历史相位与当前因果航向，再接已有07/08角差辅助证据；运行阈值先用实际正常/异常区分能力评估，不把P95当最坏误差界，不承诺零误检/漏检。
4. 验证暂停边界、恢复不重放和原围栏重获；只做直接相关检查。必要地面验证用原入口，位置/角度真值仍由独立标线或测量提供，不给F405追加测试程序。

本轮定案不要求F405新增字段、ISR、握手或新鲜度检测；已有转发核查请求保留其原范围，不重复扩大。当前未修改运行代码/协议或部署候选；后续每小步分别回传文件、检查、实测/未测项及commit/push。
