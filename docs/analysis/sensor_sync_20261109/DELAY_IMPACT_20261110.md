# 当前延迟的影响与建议

2026-11-10，代码分析基线fb32fc5；依据既有MotionDebug与两场正式日志，没有新增实车动作。本轮只做离线计算及文档，不改变运行逻辑、安装、比例、来源或下位机。

## 判断

现在有两种不同的问题：主gyro相对其他运动观测约28ms的重复相位差，以及雷达到达/结果可用、测试Pose消费的偶发长尾。前者主要损伤转动时的一致性，后者会让修正和原始Pose迟迟不能被使用。热力图的雷达3.7ms是转动响应在接收时间轴上的相位差，不是雷达定位3.7ms就能算完；T2654.5ms也不是其物理运动到完整控制链的绝对延迟。相位数据不能直接乘平移速度当距离误差。

## 对当前代码的实际影响

| 位置 | 已核对行为 | 延迟影响 |
| --- | --- | --- |
| motion_runtime.cpp current() | 输出yaw查询主gyro历史，超出支持末端保持最新值 | 主gyro相位滞后会进入当前导航航向；100Hz更新不能消除这约三拍的动态误差 |
| motion_source_native.cpp wheel() | 在MCU轮区间查询主gyro yaw，旋转车体系速度到场地 | 转弯并平移时会投错方向，即使轮速度幅值正确也会出现位置误差；轮滑仍是另一问题 |
| dynamic.py trajectory()/deskew_points() | 主gyro提供各点及扫描参考时刻yaw，位置来自所选运动历史 | 整体航向错相和扫描内相对去畸变误差需要分开，不能都算成同一个4.2°畸变 |
| f405_wheel_measurements.cpp prepare() | 等区间右端gyro，对同区间积分后生成SDK速度 | 当前MCU时间配对不等于物理响应已对齐；全局把gyro戳减28ms会使该等待额外增加约28ms |
| fusion.cpp T265FieldProjector::project() | 相机中心→车中心用同一SDK样本的完整四元数/角速度 | 这里没有直接使用外部主gyro做杆臂补偿；不能将外部gyro延迟直接归因为该输出外参错误 |

### 1. 航向与雷达

以28ms作为工程候选，60/120/150°/s转动时的动态角差量级为1.68/3.36/4.20°。若把该旧方向直接用于当前坐标投影，4.2°在1m距离处对应约73mm横向差；这只是几何量级，不是本批测得的73mm定位误差。

匀速旋转、点时刻与参考时刻都使用相同延迟的gyro时，θ(t_i−τ)−θ(t_ref−τ)中的固定延迟可在相对转动中抵消；整体场地yaw仍落后。加减速时不能抵消：相对角误差约α·τ·扫描跨度。以500°/s²、28ms、40ms有效扇区跨度为例，扫描内角差约0.56°，1m处约10mm。这个角加速度是说明性假设，并非本次标定值。

前次原始点分析已表明：192842正反180°用原gyro时标的墙面RMS为18.43/18.11mm，跨动作使用约26～27ms时间对齐后仍为8.39/6.77mm。这支持修正时间关系，但不是地面XY精度验收，也不能证明所有雷达拒绝/降级都由它造成。

### 2. 轮滑判断与官方速度输入

新离线核对使用同14动作、3174个真实轮端点；编码器固定有效轮臂0.115m，未重拟合。对100ms窗口分别计算编码器角变化和主gyro累计yaw变化，比较原时标及将gyro历史查询向后28ms的候选。该操作利用已记录的后续样本，只有离线意义，不代表在线应等待28ms。

| 绝对角速度残差 | 原时标 | 候选对齐 |
| --- | ---: | ---: |
| P50 | 3.49°/s | 0.78°/s |
| P95 | 11.40°/s | 4.73°/s |
| 最大 | 21.57°/s | 9.58°/s |

14动作各自RMS均下降。残余还包括轮地关系、轮臂、量化、gyro/时间模型等，不能据此自动设判滑阈值。α=500°/s²时，未对齐的28ms本身就可能形成14°/s角速度差；抵墙对称平移空转又可能没有角速度差。因此先处理时序，再评估角残差，仍需平移证据判断轮式是否可信。

对同一批数据，在精确轮区间内将gyro角速度积分查询平移28ms，输入杆臂项变化的模长P50/P95/最大为0.00367/0.01395/0.02624m/s。SDK输入已经按相机中心与相机轴定义，旋转不改变这个差值模长。这个量表示候选对齐将改变的输入分量，不是实测总注入误差，也不是SDK漂移上界。正常匀角速度时该差趋小，加减速更明显；不据此调整安装杆臂或SDK噪声强压结果。

正常正式轮反馈RX→SDK API的P95约11～12ms，其中等区间gyro中位约5ms，配齐后约1～4ms。物理代表时刻还含约10ms平均轮区间的中点关系，不能只看API耗时承诺整个链小于10ms。[匹配本机版本的Intel SDK v2.50.0接口](https://github.com/IntelRealSense/librealsense/blob/v2.50.0/include/librealsense2/hpp/rs_sensor.hpp#L595-L606)只有传感器ID、帧号和速度，逐样本没有时间戳参数；不能靠改frame_num让晚到输入回填到过去。

### 3. 雷达后验与100Hz控制

两场扫描参考→结果P95约102/130ms，最大192/471ms；第二场另有原始包收齐相对日志点时刻最大约277ms、计算前等待最大约396ms。后两项时间范围与前者包含/交叠，不能相加。接收残差含时钟锚点/映射，不能全部指认为计算或驱动延迟。

有正确历史传播时，车以1m/s运动且后验晚130ms，并不必然错13cm。若先验速度在这段相差20%，仅该段传播误差量级约26mm；471ms对应约94mm。这是说明性匀速模型，没有用命令值当真值；打滑/跳变可能更复杂。延迟越长，对短期先验可靠性的依赖越强，所以压长尾与修双异常来源仲裁都必要。

另外，测试Pose消费曾出现0.75～2.47秒长尾，而正式两场通常为P95约2～3ms；二者不能混称T265内部很慢。末段慢调的秒级耗时另有低速控制证据：75mm段2.08秒、91%采样平移低于20mm/s，D=0后交接约0.07秒。减少几毫秒相位或计算不能单独解决这一行为。

## 建议顺序与需要人决定的取舍

1. **先消除不稳定积压。** 正式优先定位/压缩雷达接收和计算前等待，保持已有最新扫描有界交接、历史校正和100Hz当前先验；接收路径只保留必要获取/原始记录，把逐点对象/序列化工作移出接收关键路径。当前已分进程、已有C++提线和异步日志，不把它们再当尚未实现，也未证实某个syscall就是全部根因。测试侧复用已有异步快照消除Pose同步输出尾段阻塞。暂不换几何算法或内核。
2. **再做gyro相位修正的小范围对照。** 推荐先保留主gyro场地参考：雷达历史查询采用候选对齐；当前航向另用短时预测到当前估计时刻，计算开销很小，但角加速/噪声会带来预测误差。说明性恒角加速度500°/s²下，一阶28ms预测的剩余角误差约0.196°，不是已实测效果。预测值和原始样本身份应分开，不能伪造新传感器帧。
3. **另一条可行路线是SDK短时旋转增量。** T265正常时以其短时增量补齐转动响应，主gyro仍给场地参考及失效后备。它有更直接的低延迟旋转证据，但增加SDK依赖和切换处理；只替换扫描内增量并不会自动修好最终主yaw落后。两条路线需比较相同原始数据及一段必要组合运动后由人决定，本轮不切来源、不部署预测或28ms常数。
4. **官方注入随后再省配对等待。** 历史雷达校正可以利用后来已收到的gyro；实时注入不能为取得28ms后的gyro额外排队。可评估用已到真实gyro做因果区间近似/有限预测，代价是角加速时的估计误差。既有右端完整配对与低延迟近似的取舍必须明确，不直接替换，也不用目标速度/T265速度充当轮反馈。保持输入/输出外参各处理一次。
5. **来源仲裁与末段控制分别处理。** 同步对齐后的轮/gyro残差才适合讨论判滑；墙/T265平移证据仍必要。已经判轮式可疑又发生SDK跳变的边界不能用优化延迟代替。到位慢调按实际较新F405实现复核，不能据旧实跑要求重复已做修改。

目前没有新增F405功能的必需证据；若进一步追查28ms上游来源，先只读核对实际IMU型号、已有输出/滤波配置和接收解析。RDK软件补偿不会让F405本地控制自动获得更快的物理角反馈。降低滤波可能换来噪声，具体取舍另由人审，不先要求新增ISR、遥测、握手或时间检查。

## 验证边界

当前能说明的是相位重复性、历史查询改变的量级及已记录的处理长尾。不能由100Hz线程频率或被动接收实验承诺正式0x16每10ms实际到达；硬实时/绑核也不能消除传感器响应差、同步I/O阻塞或不可靠的运动先验。当前普通PREEMPT/FIFO10不是PREEMPT_RT对照结果。

详细新计算见delay_impact_estimates_20261110.json；14动作与前报告相同，不是新的独立验收集。必要核对仅包括原始区间支持、数值/单位与数据表对应；没有启动SDK/UART/电机、增加运行检查、修改/清理原始日志。后续建议不等于实施授权，不新增新鲜度准入或故障锁存。
