## 快速重发为什么没走起来

1. 905.124秒首次短4，保留本局；905.914秒runner已停止旧规划。没有operator_resume_requested，也没有resume_progress非空的开赛记录。
2. 909.135秒再次按4，910.895秒触发exit_session，914.075秒清局完成。之后922.777、926.126、930.058秒短3均被拒为未准备好；948.060和955.867秒又各触发一次清局。
3. 原逻辑长4门槛2秒；用户本轮反馈都是按住一会，并明确要求改5秒。因此不是每次按4都清局，但该局3次确实达到了清局动作。配置尚未请求，不能归因下位拒收恢复包。
4. 用户另确认：按4不收纳爪，无法搬回原出发位。这是独立的下位流程缺口，不能只让用户改短按手法。

原始UART末段已校验CRC的一帧：904.909秒`a3b3170380122ee00401000039b1c3`，mode18/REMOTE_STOP，后续末帧仍同mode、ACK更新至6。注意上位operator_stop事件写入时间晚于直接UART通路；不能用两个日志写入时刻反推车提前停车。回包没有左右爪收纳角实测，用户观察与实际源码共同定位收纳缺口。

只读核对匹配b65e3c8的Main/Src/Task.c：ABORT在6400行调用task_stop(REMOTE_STOP)；587行函数只RearmConfig并进入TASK_STOPPED。8322行STOPPED只Motor_Stop及等新CONFIG，不执行收纳。Claw_Retract只在新一轮task_initialize后的initial_claw_ready阶段调用（7985行）。这就是把搬车前动作拖到了按3以后。

当前修补：长4两条识别路径均5秒，按下立即STOP不变，长3仍1秒；提示明确松4保留本局。13项必要离线检查通过，覆盖持续按住与松开补判、热进程/进度保留/旧恢复不能覆盖新STOP。未启动设备，必须重开整个正式入口加载。

下位请按MATCH-ROUND-RESUME-STOW-20261117补人工ABORT后原收纳姿态；只读核对源代码，不在RDK修改或烧录下位。
