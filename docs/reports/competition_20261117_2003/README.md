## 黑块误清障：自身载荷换号后被当成爪前地面物块

第一次触发在相对325.986秒（5分26秒），关联第8174帧、录像clip10第33帧：

- 140°抓后/运输确认的黑块编号513。
- 相机140→120°过程中，513框断开，325.090秒起新黑框544出现；画面显示黑三棱锥贴着左爪内侧。
- 544框为(279,627,143,101)，底边中点(350.5,728)。实际人工扫障曲线包住这个脚点，因此被通道判障函数当成候选。
- 载荷换角重关联另用固定平台范围：120°四点(390,735),(910,735),(960,895),(310,895)。544脚点在范围外（不只Y差7px，左侧范围也不覆盖），所以不能从513接续为已确认载荷544。
- 判障的另一条同类重叠排除只在画面底部20%（Y≥819）适用，本框Y728也不满足。
- 结果是：新的544既不在旧载荷ID排除表，也没通过平台换角接续，进入了同类障碍列表。geometry_check.json用原保存曲线及真实框调用现行同一函数复算，障碍确为544。
- 该画面其他物块只有顶部橙色框，位于安全区范围/推进通道前缘之外；没有绿色候选触发本次清障。不能把此前用户对“区内绿误触发”的疑问直接当本局原因。

[第一次触发原图](clip10_frame033_original.jpg)。图上可见原爪ROI、人工扫障曲线和自身左侧黑块。人工扫障曲线表示“地面上的物块若位于此通道会挡路”；不能直接证明其内每个检测框都是地面物块，必须先可靠扣除本车载荷。单纯缩窄扫障曲线可能把真正挡道物排出去，并非本问题的直接修法。

实际流程区分：这一回上位选择kind=pickup（同类障碍先寄存原货、抓同类、再找回），并非全开爪横扫1000mm分支。日志message固定带“横扫1000mm”在pickup情形只是误导性共用文字。原UART确认326.032秒下位接受58034，随后58035/36/37/38分别执行原暂放、退回、转向，331.251秒58039完成回SEARCH；不是只有上位发请求。

之后重新抓取黑块564，运输中再次暂缺框并沿原确认载荷复用；变120°后出现568，脚点(352,732)仍在旧载荷平台范围外。相对351.55秒起重复触发相同问题。[第二次原图](clip10_frame122_original.jpg)。该段约47个不同清障action被下位拒绝，保持原ALIGN58048，不能把这些请求记成执行47次。黑块后来移到画面右侧后最终进入推进；拒绝重发循环另须核对处理，不能靠减少一次检测或把所有同类框排除来掩盖。

建议最小后续方向：围绕“已真实确认、保持闭爪”的载荷换角接续，核对115/120°左右爪实际持载位置及现有固定平台范围，并处理已确认物块换ID后不再被当成地面障碍。保持真正同类地面障碍可见，不能全局忽略黑块或同类别；边界怎么确定及采用何种接续证据需先结合本局图确认，未获授权不直接改人工ROI或载荷判定。
