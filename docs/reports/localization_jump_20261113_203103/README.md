此前已有T265/轮式位移冲突，来源为WHEEL_FALLBACK；这表示两路不一致，并非独立证明哪一路绝对正确。
本趟534.460s进入ALIGN_SAFE_ZONE_BY_POSE后，业务safe_zone_low_speed策略暂停新轮式影响。
worker事件1913865031753ns明确把WHEEL_FALLBACK切到T265_PHASE_NO_WHEEL，保留选定位姿与SDK之间的旧对齐偏置。

正式提交的NativeMotionSource::ingest_pose在phase_wheel_suppressed时只看confidence>0便publish_vio后return；
常规process/fallback在此阶段也直接return。因此阶段禁轮绕过了常规冲突/跳变降级，confidence=3的坐标突变直接通过。
对应已提交源码f7be125:localization/src/motion_source_native.cpp约114–150、257–273、330–350。
工作区另有归档中的实验改动，不能据其存在宣称本次实跑已经桥接跳变。

最后一次SDK轮速调用在1913814690227ns成功返回；随后策略已暂停新发送。
最后一包来自真实轮反馈，v_B=(0,0,0)、omega=(0,0,0)，不是人为错误注入，也不是目标速度。

API返回成功只证明主机调用；本次没有内部融合权重/重定位原因的独立回执。

## 雷达为什么没拉回，为什么恢复轮式也不立即纠正

跳变附近雷达rank_xy=0，没有新的XY解；map_translation_offset未出现对应2m跳变，因此不是雷达把位置吸到对面。
跳后到传感器记录结束约40.7s：410帧结果中409帧无可观轴，仅1帧Y轴小修约+24mm，没有双轴重获位置。
失败原因主要为NO_SUPPORTED_WALL_AT_OPERATOR_BRANCH、局部残差/修正边界及两轴证据不足。
那一帧虽reason字段写STATIC_GEOMETRY_DIAGNOSTIC_ONLY，实际Y偏置变了24mm，不能仅按标签说全无修正。

低速阶段结束时，又将偏移后的选定位置作为轮式恢复锚点；1933254832265ns重新进入WHEEL_FALLBACK，
其绝对基准已受污染，切回轮式不会凭空恢复真实场地位置。
550.884s返程按错误坐标约(-0.041,-0.711)m向目标(0,+0.30)m算出1012mm剩余距离；错误已进入导航，不只是显示。
最终估计回到(0.129,0.342)m，主要发生在恢复运动传播后，末段只有上述Y小修；没有独立地面真值，不能把“图又回己方”当精度恢复。
