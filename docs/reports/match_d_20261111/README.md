## 代码事实、最小改法与未知

对应e85参考 `Task.c:3421—3441` 在STAGE NAV D=0到位时提前设置120°；`:1446—1465` 进入mode48又设置140°；合法审核后的ALIGN再次设置120°。两轮回包可见这个冗余往返。最小切角改法是STAGE到位保持140°，复审通过、接受ALIGN后再按原逻辑切120°，不增加等待或握手。**这只能消除冗余切角，不能把约60ms交接说成已解释13.513秒长停。** 本报告未实施此改法，下位修改仍须按当前协作流程审查。

参考 `Task.c:6506` 的mode48在没有合法审核时会等待、按既有3.5秒窗口复看最多两次，此后仍依赖真实审核通过；原始日志证明等待持续存在，但不能仅凭局部目标推定哪种载荷结论才正确。

下位参考源码另有独立约束：递增 `vision_frame` 可判新图，但审核计数仍按不同 `audit_id` 去重，并要求100ms样本间隔；同ID新帧不等于新增第二个样本。因此不能从上位首个STABLE开始永久固定ID，否则下位可能只收到一个样本、永远不能READY。

本次未确定：局部黑三角真实爪内外位置；开局mode1长段的内部机械/控制子阶段；两个CLUSTER丢失恢复的物理原因。对这些不擅自放行未知载荷、不改模型阈值或相机标定，不把下位源码潜在缺陷说成现场唯一根因。

## 本轮上位机修复及实际检查

1. **新画面导致报文确认追逐。** 原逻辑每来一个真实新帧就更新audit_id，却要求relay恰好回报上一帧的完整报文。用原状态机持续送20个合法单绿新帧、relay落后两个图像帧，即使MCU已READY/VALID，仍不能退出TRANSPORT_AUDIT；停止换图让relay追到最新报文则立即ALIGN。这是代码复现，不代表已证明它是两轮最长停顿的唯一原因。
   现仅在MCU已经READY/VALID且当前审核动作已接受后，若相邻STABLE审核的类别、左右、数量及全部业务标志完全相同，短交接期间复用前次报文ID，真实source frame仍逐帧更新。READY前继续产生不同ID。确认仍要求实际当前完整8字节报文已发出及当前动作接受，不放宽通用匹配、不缓存旧epoch授权。缺框、换角、左右/类别等改变仍按原逻辑撤销/更新；同ID不被当成刷新下位证据。
2. **重复拒绝清掉已接受审核。** 原运输回退只看REJECT，即使同任务、同action、同opcode同时已有ACCEPT，仍会增加audit_epoch、清空两帧证据。现在保留该已接受动作；HOLD/PAUSE不当机械请求；真正未接受请求仍以新动作进入原复审，不忽略全部REJECT。
