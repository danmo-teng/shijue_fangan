# 前后九局雷达定位对比：修正率下降主要卡在哪里

本轮先完成用户授权的分段测距交接修复96936aa，再按用户补充要求扩大到前几次实跑比较。以下仅离线分析，没有修改定位算法/阈值、启用实验融合、增加运行诊断或启动设备。

用户本轮补充的现场事实：从昨晚23:29到凌晨几局，**没有动雷达、围栏或出发摆放朝向，但凌晨灯光更暗**。不能把未发生的安装调整写成原因，也不能仅凭光照变化直接认定全部故障都是T265。

## 对照范围与统计方法

compare.py读取九局原dynamic_localization.jsonl；先按正式参考建立后的前30秒对齐，再看最多前180秒/该短局已保存部分。不是拿整局不同长度或停车后数据直接相除。最近短局按最后业务记录截断；已知STOP的局也按STOP截断。引用字段reference_ns，故与上一报告按写记录时刻截断可能相差1条记录。

“可采用比例”是这一条扫描最终至少有X或Y一个方向用于修正，不是地面精度或成功率。“候选墙线总体残差”是点云与拟合围墙的偏差指标，不是车身的位置误差；实际算法逐轴检查，不能简单把整体RMS高于3.5cm等同两轴都不合法。

## 1. 点数没明显变少，也不是提取不出线

九局每次处理的physical_points中位均177，安装外参、145°工作窗口及坏角屏蔽记录一致。前180秒候选线数中位：好局20:03/23:29为2，最近末局为3，**不能继续把问题概括成候选线少了**。关键是这些候选不能按当前航向和场地模型构成可信围墙。

从23:29上位bca14a4到当前，static.py/dynamic.py/diagnostic.py/scan_geometry.py无提交差异；18:03→20:03也没有定位模块提交差异。磁盘仍有未提交实验，未改/未恢复它们；实跑worker开关是experimental_robust_localization=false。相同参数和代码不保证实际墙匹配相同，但没有证据是本轮把门槛调严了。

## 2. 现在大量失败在已有墙线的几何检查

现有流程：至少12点、足够长的线段提取→外层候选→按主陀螺航向旋转→距离某围墙20cm内且方向差12°内的候选→拟合XY→逐轴3.5cm残差及场地包围检查。最后一项会拒绝把一条线中大量点放到场地外的候选。不是用T265高置信度、导航已到点或数据年龄拒绝雷达。

比较各局前180秒（短局只有约31秒）：

- 23:29共1799条，1759条可采用，40条失败。其中27条只有wall_residual、13条同时残差与包围关系不通过。
- 最新末局1798条，215条可采用，1583条失败。其中412条只有wall_residual、1075条同时残差与包围关系不通过，96条未找到可关联的围墙。
- 最近短局312条，23条可采用；122条未找到可关联围墙、51条仅残差失败、116条两项都失败。

因此最新长局多数不是“预测位置离墙超过20cm，所以根本不找了”，而是**已经有候选墙线，拟合后依然与固定方向/场地形状不一致**。最近末局还有42条“只提到1条线、只关联1面墙，但残差仍不通过”的样本。纯XY平移可以被同一面墙的拟合吸收，不能把这类残差全解释成位置先验偏了一点；仍可能是线本来不是墙、当前方向与真墙不符或扫描补偿问题。没有该时刻线法向/原点云，不能进一步唯一判定。

## 3. 不能只怪转弯太快或CPU赶不上

用已记录下位轮速和主航向变化粗分：轮速<0.03m/s且角速<3°/s为低运动组，不用T265的速度来反证T265本身。该分类仍非外部地面真值，推车/打滑等特殊情况需另辨。

前180秒/短局：23:29低运动组556条，可采用100%；00:48为607条、51.73%；03:41为623条、19.42%；最近末局615条、15.61%，最近短局114条、0.88%。最近的差距在低运动时仍然存在，单靠“转快了”不能解释全部。

按航向模90°的三个角度区间比较，23:29各区间均约97%～99%，最新末局约7%～16%，也不是仅因最近恰好更多朝某个方向。后期计算耗时确有增加，但程序在失败后会尝试额外围墙重找，本身就可能增加计算；现有数据不能把这解释成处理延迟导致拟合失败的单向因果。

## 4. 用户补充的暗光：重要候选，尚不能定为全部原因

[RealSense官方说明](https://dev.realsenseai.com/docs/intel-realsensetm-visual-slam-and-the-t265-tracking-camera/)明确指出，光照不足会让T265难以提取视觉特征，较低照度还会增加噪声、延长曝光并造成模糊。故暗光可能先影响T265，再通过运动估计/补偿等环节影响定位。

但当前记录不足以证明该完整因果链：

- 前180秒T265高置信度比例：好局20:03约97.08%、23:29约98.14%；03:41约97.70%、最近末局约98.27%。没有对应雷达大幅退化的持续失跟/低置信度暴增。高置信度不能证明位置准确，也不能单靠这些数排除暗光。
- 好局20:03和23:29也约在参考建立后1.3秒切到T265/轮程不一致的轮式后备，随后雷达仍有约98%的可采用率。近期的这条切换不是新出现，也不能单独解释雷达下降。
- 固定场地航向取自主陀螺，不直接拿T265姿态当雷达航向，因此不能简单写成“T265受暗光影响，雷达方向就一定错”。可能的间接链条需要对应数据验证。
- 最近低轮速/低角速时也大量失配，原来安全区禁轮恢复遗漏仍会放大定位问题，但该遗漏在较早好局也存在，不是本轮唯一新增触发因素。
- 这些会话没有保存逐次失败所用的完整点云、线法向及T265鱼眼图。UVC物块相机的画面亮度不能替代T265图像质量证据。末尾dynamic_status点云大多晚于赛程分析窗口，已检查但不拿它冒充中段失败现场。

因此当前已查清的是**什么条件挡掉了数据，以及前后确有巨大差异**，物理根因尚未唯一坐实。按用户“未动雷达/围栏/出发朝向、只有光照更暗”的反馈，优先验证照明这一变量合理，但不擅自认定安装变了，也不直接放宽雷达门槛或关闭T265。

## 下一步建议（未执行）

保持代码、起点、场地和参数一致，把照明恢复到之前水平，做同一段开局约30秒对照；先用已有日志比较雷达采用率、残差及实际观察点位置，无须新增全量日志。若亮度恢复后仍差，再讨论只保存少量失败扫描所用点/线与对应主航向，确认是墙面选择、方向参考还是补偿问题；新增采集范围和开销须另获用户确认。本轮没有开启这些采集或动车。

原数据统计在comparison.json，T265辅助对比在t265_comparison.json；compare.py为离线复算脚本。九局比较不等于九次新的设备测试，也不等于雷达/地面精度已验收。
