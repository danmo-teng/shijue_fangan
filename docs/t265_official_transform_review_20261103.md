最新日志独立矩阵重算与现程序一致。它不能修复SDK源位置本身的跟踪误差。
代码职责确实混杂，建议在原入口内抽出纯几何转换；不需要重写整个localizer或新增一套测试入口。

## 最小数学定义

约定R_AB把B轴表达的向量转为A轴表达；W为SDK世界，C为SDK定位中心，B为车体中心。
SDK给出p_WC、R_WC、v_WC及omega_W；车体X前/Y左/Z上。

已确认固定量：

```text
forward_C = (0.8660254, 0, 0.5)
up_C      = (0, -1, 0)
left_C    = up_C × forward_C
R_CB      = [forward_C, left_C, up_C]   # 按列排列，归一化
r_BC^B    = (-0.0346105, -0.0599471445, 0) m
```

于是纯几何只需要：

```text
R_WB = R_WC · R_CB
r_W  = R_WB · r_BC^B
p_WB = p_WC - r_W
v_WB = v_WC - omega_W × r_W
v_B  = transpose(R_WB) · v_WB
```

场地参考另做一次固定变换：

```text
p_FB = p_FB0 + R_FW · (p_WB - p_WB0)
R_FB = R_FW · R_WB
```

最后从R_FB的车头方向提取平面yaw。以当前初始水平投影确定R_FW，
车中心起点与场地初始方向属于参考定义，不属于安装外参。
位置与速度都在同一参考系内相减；不能给世界速度直接减车体系杆臂项。

数值核对：R_CB行列式≈1，`R_CB*r_BC^B≈(0,0,-0.069221)m`。
即当前候选下，B→C杆臂在C轴里近似沿光轴负Z。输出减去这一次旋转杆臂，输入轮速按B→C加omega×r一次。
SDK Pose已是官方定位中心，不能再手工加入估计的内部IMU偏移。
这里沿用用户已确认r_BC.z=0的平面候选；若未来定义完整3D目标点并要求处理高度杆臂，必须先测量和确认Z，不猜值。

## 已发现的具体结构/参考问题

1. `T265FieldProjector::project`在confidence判断之前初始化参考；本会话frame0 confidence=0，
   第一个输出CSV是frame1/confidence=2。若误用CSV首行当原点，重算出现最大约0.21mm/0.00879°差异；
   改用原始首帧后回到上述舍入误差。这是确切的初始化策略问题，本次数值不足以解释严重缩短或1.327m异常。
2. 一个projector同时做刚体变换、起点/场地映射、比例、yaw滤波/积分与诊断，引用完整LocalizationConfig。
   不利于把几何输入输出单独看清。纯转换可是不持有起点、滤波、时钟门或串口状态的独立函数。
3. main.cpp约2123行，既有测试SDK、正式启动/地图策略、UART/导航、滤波和输出；
   地图脚本约1398行兼有GUI/进程/动作/记录。行数不是错误证据，但这些职责共用入口增加认知和回归成本。
4. 源码仍有“lens-up”等历史注释，与当前水平视线候选不一致；应在批准的小步整理中改为明确W/C/B术语。
